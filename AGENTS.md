## Code style

- Make clean and simple code. Do not over-engineer, stay KISS.
- Code reads as it executes. Keep orchestration at one level of abstraction. Express meaningful steps as named functions, with implementation details inside those functions, without splitting into micro functions.
- Reuse code. Keep a single source of truth.
- Infer types as much as possible. Use explicit types to model a contract.
- Make permanent code only: no temporary workarounds.
- Trust the types and the framework: add checks and try/catch only when the user asks.
- Keep the default behavior of libraries and frameworks unless the user asks otherwise.
- Keep implementations minimal within clear responsibility boundaries. A distinct responsibility with an established contract gets its own type and implementation, even with a single caller.
- Use the language, tools, framework and libraries before you write your own.
- If the current implementation does not fit a new need, rework it first.
- Add code, configuration or special handling only for a requested behavior or what it needs to work. Leave unrequested edge cases to the existing behavior.

## Backend conventions

- Each resource lives in `src/lib/<resource>/`, with one file per operation, and is registered in `src/lib/di/container.ts`. `src/lib/notes/` is the reference.
- Use the operation vocabulary Create, Info (by ID), List (offset/limit pagination), Update, Delete.
- Give Create and Update their own request DTOs, even when their fields currently match. Map each response with the resource's `toResponseDto`.
- Delete is idempotent: deleting an absent resource succeeds with 204, without an existence check.
- Create an entity-oriented service only when multiple operations already share the same behavior.
- Define request schemas with Zod in the resource's DTO files and validate them at the route boundary with `sValidator` from `@hono/standard-validator`. Operations receive validated data; business validation stays in the operation.
- Represent expected business failures with the helpers of `src/lib/errors/error.factory.ts` and a typed error code. Routes let these errors propagate.
- Add no test framework or persistent tests. Use ad hoc checks to verify behavior.

## Database

- After a change to `src/lib/db/schema.ts`, run `bun db:generate`, then `bun db:migrate`.
- `src/lib/db/auth-schema.ts` is generated by the Better Auth CLI. To change it, change `src/lib/auth/auth.ts` and generate it again.
- After a change to `wrangler.jsonc` or `.env`, run `bun types:generate`.

## Linting and formatting

- After code changes, run `bun fix`.
- Before you finish, run `bun check`.
- Fix actionable lint and formatting issues. If a rule would contort otherwise clear, idiomatic code, keep the rule configuration unchanged and report the rule, location and proposed resolution for arbitration.

## Commits

Use conventional commits, for both commits and PR titles.
